# 13 — Operations: where they start and end, how the tree is built anywhere, and how to find one

## 1. An operation is delimited by code, never guessed from log lines

- **Start** = a call to `Operations.Start(...)`. **End** = `Complete(...)` or `Fail(ex)` on the returned `ActiveOperation`.
- **Parent** = the operation that was ambient (`Operations.Current`) at the moment of `Start`. Async code keeps it across
  `await` (`AsyncLocal`).
- **Root** = an operation started with **no** ambient operation. It creates a new `TraceId`.
- Developers rarely call `Start` themselves: generated code and framework choke points do it at every known boundary.

| Boundary | Starts when | Ends when | Generated by / lives in |
|---|---|---|---|
| `[StateCommand]` (UI action) | the command method is entered | its `Task` completes (ok / cancelled / faulted) | State generator wrapper |
| Undo / Redo | `UndoManager.Undo()` | the state is restored | History observer (12 §3) |
| Navigation | `NavigateTo(...)` | `OnNavigated` (or guard denial) | NavigatR navigator |
| CQRS command/query (client) | dispatcher entry | result returned (`QueueableResult`/`CacheableQueryResult`) | Cqrs `LoggingStage` |
| RPC call (client) | proxy method entered | response or exception | generated Fusion proxy |
| Handler (server) | `IHandlerInvoker` entry (continues the client's trace) | handler returns | `TracingHandlerInvoker` |
| HTTP request (server) | middleware entry (continues a trusted caller's trace) | response finished | `UseYFexLogging()` |
| HTTP call (client) | `SendAsync` | response headers received / exception | `TracingHandler` (YFex.Web) |
| SQL | command execute | reader closed / execute returns | YFex.Data executor / `TracingDbConnection` |
| Job run | job invoker entered (new root) | job method returns | `LoggingJobObserver` |
| Saga step | step dispatch | step result / compensation | Orchestration generator |
| Event handler | `[Subscribe]` adapter entered | handler returns | Messaging generator |
| Anything custom | `log.Operation("Name")` | `Complete(...)` / `Dispose` (→ `Unknown` if never completed) | developer |

## 2. Roots per kind of host

| Host | Roots are | Notes |
|---|---|---|
| Avalonia / Blazor / Uno app | **user actions** (`[StateCommand]`, navigation, undo/redo, dialog results) and **system actions** (`[Poll]`, `[Live]` refresh, sync, timers, kind `system`) | the viewer separates "what the user did" from "what the app did by itself" |
| ASP.NET Core / RPC server | each incoming request/call; continues the caller's trace when trusted (05 §2) | a click on a desktop and its server work share one trace |
| Worker / Jobs host | each job execution, each consumed message | linked (`FollowsFrom`) to whatever scheduled/published it |
| Console app / CLI tool | each top-level command: `await YFexConsole.RunAsync(args, "Importar NFe", ct => …)`, or `using var run = log.Operation("Importar NFe")` in `Main` | a menu-driven console makes each menu choice a root |
| Code outside any operation (startup, static init) | none: records are **untraced** | shown in the node's **process timeline**, ordered by time and sequence |

## 3. When a trace is "complete", and stragglers

- A trace is complete when its root has ended **and** all its children have ended, or after a 30 s grace period.
- Fire-and-forget work (`_ = Task.Run(...)`) inherits the ambient operation and stays a child. If it outlives the root, the
  waterfall marks it `detached`.
- Intentional background work should start its **own** root with a link: `Operations.StartLinked(descriptor, OperationLink.FromCurrent(LinkKind.FollowsFrom))`.
  This keeps traces short (same rule as offline replays, 05 §4).

## 4. The tree is data, so it renders anywhere

Every operation-end record carries `TraceId`, `OperationId`, `ParentOperationId`, start time and duration. The tree comes from
**parent ids, not timestamps or text**. It survives clock skew, interleaved threads, multiple machines and any output medium.

| Where | How |
|---|---|
| **Console** (`.WriteTo(w => w.Console(c => c.Tree()))`, default in the Development profile) | prints a trace as a tree when its root completes; plain lines for untraced records |
| **CLI** `yfex-log` (reads `.ylog` files or the server) | `yfex-log activities --user joao --since 10:30`, `yfex-log trace 4BF9-2F35` |
| **LoggY / web viewer** | waterfall, edit timeline (12), links to replays/sagas |
| **In-app diagnostics panel** (Memory/LiveTap sink) | last traces of this session; "send to support" |
| **Tests** | `capture.Trace.ToTreeString()` + assertions |
| **OTLP backends** (Aspire dashboard, Grafana Tempo, SigNoz) | same tree: `TraceId`/`OperationId` map 1:1 to W3C trace/span ids |

## 5. Finding one user's operation among millions of records

Five layers, each cutting volume by orders of magnitude:

1. **Activities, not records.** The default list shows **root operations only**: one row per thing a user or the system *did*.
   The server materializes an `activities` table from root operation-end records (trace id, name, user, tenant, session, device,
   node, start, duration, outcome, child count, error count; indexed by `(tenant, user, start)`). Order of magnitude: 50 M
   records/day → ~400 k activities/day → one user's day → ~300 rows.
2. **Who / what / how / when filters:** `user:joao tenant:acme/loja7 kind:ui outcome:faulted dur>1s since:10:30 release:1.4.2`.
3. **Search keys.** Ids marked `[LogValue(SearchKey = true)]` (`VendaId`, `ChaveNFe`, `PedidoId`; ES `[StreamKey]` aggregates
   automatically) are indexed in a `search_keys` table `(key type, value, trace id, time)`. Typing `V-88123` returns **every
   trace that touched that sale**: the click, the server handler, the offline replay two hours later, the saga, the nightly job,
   the NF-e emission. Sensitive keys (a customer's CPF) are indexed as their hash only.
4. **Support code.** Every error the user sees carries a short code, the first 8 hex digits of the trace id (`4BF9-2F35`).
   YFex.UI.Abstractions' `IMessageBox`/`IToast` error variants add it automatically. Server errors return it in the
   `traceId` of ProblemDetails / an `X-Trace-Id` header. The user reads it to support, and support pastes it.
5. **Session journey.** User → sessions → their activities in order, with navigation breadcrumbs and edit timelines (12):
   "what did João do in loja7 between 10:30 and 10:45?"
