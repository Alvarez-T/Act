## 2. The shape of the solution: four layers, one job each

```
 ┌─ 1. Field metadata (framework-neutral, generated at build time) ─────────────────────────┐
 │  FormShape<TModel>: fields in order, typed get/set delegates, editor kind, size, group,   │
 │  editable-in modes, visibility rules, child shapes, element shapes.  No UI types.         │
 │  Sources: the C# declaration + type hints on value objects + few [Field] attributes.      │
 └───────────────────────────────────────────────────────────────────────────────────────────┘
 ┌─ 2. Live behaviour (already owned elsewhere, read through contracts) ──────────────────────┐
 │  IValidationSource (Validation + Rules decisions) · INotifyPropertyChanged (State)         │
 │  classification masks (Privacy) · permissions (Authorization, field-level is a request)    │
 └───────────────────────────────────────────────────────────────────────────────────────────┘
 ┌─ 3. Editor choice (per platform) ──────────────────────────────────────────────────────────┐
 │  EditorKind + T → the Y input. Compile-time dispatch, app overrides per type.              │
 └───────────────────────────────────────────────────────────────────────────────────────────┘
 ┌─ 4. Layout (per platform) ─────────────────────────────────────────────────────────────────┐
 │  YForm: columns (max 3), size presets, sections, collapse, responsive, modes.              │
 │  Works with generated fields, hand-placed fields, or any mix.                              │
 └───────────────────────────────────────────────────────────────────────────────────────────┘
```

Why split this way:

- **Metadata never references a UI framework**, so Avalonia, Uno, Blazor and later Composer render the same shape (YFex.UI rule 3, "one API, every platform").
- **Behaviour stays with its owner.** The form does not validate, decide rules or check permissions. It asks `IValidationSource` and the other owners. A form with no Forms package still validates the same way (the inputs already do).
- **Editors are the existing inputs.** No `YFormTextBox`, no wrapper per type. A new value object gets an editor by declaring hints on its type, not by a new control.
- **Layout is a panel**, usable without any generation at all (a hand-written form gets columns and sizes too).

## 3. How metadata is produced: options compared (⚑FM2)

| Option | How | AOT / trim | Cost per keystroke | Escape hatches | Verdict |
|---|---|---|---|---|---|
| **A. Source generator → static `FormShape`** | `[Form]` on the model; generator emits fields, accessors, editor dispatch, a module initializer that registers the shape | safe: delegates and generic statics only | zero metadata cost at run time | everything generated is data; overrides at every level (§5) | **recommended** |
| B. Runtime reflection (`PropertyInfo`, `TypeDescriptor`, `Activator`) | read attributes when the form opens | breaks trimming and Native AOT; `TypeConverter` is not trim-safe (all-projects rule) | reflection per open, boxing per value | easy | rejected (ecosystem principle) |
| C. Scaffolding only (a tool writes `.axaml` from the model once) | `yfex forms scaffold CustomerEditModel` | safe | none | full freedom, but the file drifts from the model on every change | keep as an **extra** ("eject", ⚑FM28), not the base |
| D. Runtime JSON descriptor | layout stored as data, interpreted | safe if the interpreter is | interpreter | end users can change it | that is **Composer** (⚑FM16); Forms produces the same descriptor shape so Composer can render it later |
| E. XAML-only conventions (`DataTemplate` per type) | Avalonia `DataTemplates` keyed by value type | needs `DataType` templates; no order, size or group info | low | weak: no metadata | use only for the "editor per type" piece, not for forms |

The generator approach is the same family as System.Text.Json source generation and PolyType (a shape generator by the STJ author): a static description of the type plus a typed visitor, so generic code calls `field.Accept(visitor)` and the compiler, not reflection, knows `T`. We take the pattern, not the package (third-party rule; ⚑FM2 lists it as a rejected alternative).

## 4. The model side: what a developer writes

### 4.1 Rules for annotations (⚑FM3, ⚑FM4)

1. **Annotations go on UI models (`CustomerEditModel`), never on the public contract (`Customer`).** The domain rule says contracts carry no extra behaviour attributes; UI models are one per screen shape and belong to the presentation project. This also keeps domain modules free of any UI reference.
2. **Most fields need no attribute.** Defaults come from three places, in this order:
   1. **the value type** (declared once on the type: `CpfCnpj` → medium width + document mask; `CustomerId` → tiny, read-only after create),
   2. **the declaration** (order, nullability, `get`-only, enum size, child model, list of child models),
   3. **one `[Field]` attribute** with named arguments, only where the default is wrong.
3. **Conditions are code, not strings.** `IsXVisible` / `CanEditX` properties (convention), `[Field(VisibleWhen = nameof(…))]`, or a static `ConfigureForm` block in the model; never `[VisibleWhen("Kind == 1")]`.

### 4.2 A realistic edit model

```csharp
// app/YFexFarma.Desktop.Presentation/Customers/CustomerEditModel.cs
[Form]                                                    // proposed: emits FormShape + registration
[ValidatesAs<Customer.Commands.CreateCommand>]            // exists: rules from the command, ToCreateCommand()
public partial class CustomerEditModel : StateObject      // exists: YFex.State
{
    [Observable] public partial CustomerId Id { get; set; }      // type hint: Tiny; hidden on Create, read-only after
    [Observable] public partial PersonKind Kind { get; set; }    // enum with ≤ 4 members → segmented choice
    [Observable] public partial PartyName Name { get; set; }     // type hint: Large
    [Observable] public partial CpfCnpj Document { get; set; }   // type hint: Medium + CPF/CNPJ mask
    [Observable] public partial EmailAddress? Email { get; set; }       // nullable → optional (unless Validation says Required)
    [Observable] public partial Telefone? Phone { get; set; }
    [Observable] public partial DateOnly? BirthDate { get; set; }

    [Observable] public partial AddressModel Address { get; set; }          // child model → its own section
    [Observable] public partial StateList<ContactModel> Contacts { get; set; } // list of child models → collection

    [Field(Size = FieldSize.Full, Preset = FieldPreset.Multiline)]
    [Observable] public partial string? Notes { get; set; }

    public bool IsBirthDateVisible => Kind == PersonKind.Person;  // convention: Is{Field}Visible (re-checked when Kind changes)
}

[Form]
public partial class AddressModel : StateObject
{
    [Field(Size = FieldSize.Small)] [Observable] public partial Cep Cep { get; set; }
    [Observable] public partial string Street { get; set; }
    [Field(Size = FieldSize.Tiny)] [Observable] public partial string Number { get; set; }
    [Observable] public partial string City { get; set; }
    [Field(Size = FieldSize.Tiny)] [Observable] public partial Uf Uf { get; set; }

```

Count: 9 fields, 1 `[Field]` on the customer, 3 on the address. Compare with today's Farma `CustomerModel`: all `string`, no validation, and the view repeats every field by hand twice (§1 of [02](02-crud-pattern.md)).

### 4.3 The one attribute (*proposed*)

```csharp
[AttributeUsage(AttributeTargets.Property)]
public sealed class FieldAttribute : Attribute
{
    public int Order { get; init; }                 // default: declaration order
    public FieldSize Size { get; init; }            // Auto = from the type
    public FieldPreset Preset { get; init; }        // Auto = from the type (§4.5)
    public string? Group { get; init; }             // section key; label from the catalog
    public FormModes EditableIn { get; init; }      // default Create | Edit; Id types: Create only or None
    public FormModes VisibleIn { get; init; }       // default all modes
    public string? VisibleWhen { get; init; }       // nameof(a bool member); §4.6
    public string? ReadOnlyWhen { get; init; }      // nameof(a bool member); §4.6
    public bool NewRow { get; init; }               // start a new row
    public bool Hidden { get; init; }               // keep in the model, never render
    public string? Profiles { get; init; }          // "quick", "full" (§9.4)
}

[AttributeUsage(AttributeTargets.Class, AllowMultiple = true)]
public sealed class FieldGroupAttribute(string key) : Attribute     // optional: order and look of sections
{
    public int Columns { get; init; }                // overrides the form's MaxColumns inside this section
    public bool Collapsible { get; init; } = true;
    public bool StartsCollapsed { get; init; }
}
```

Eleven named arguments on one attribute, all optional, instead of ten attributes. Anything conditional goes to §4.6.

### 4.4 Sizes (⚑FM6, built in FM-P1)

Six presets. A preset sets how much of the row the field takes (**span**, relative to the form's columns) and, in a one-column form only, a **maximum width** (a token), so an `Id` stays small on a wide screen. With two or three columns fields fill their span, so the columns line up (FM-P1 found that capped fields leave ragged right edges).

| `FieldSize` | Span (units; 6 per column) | Max width in one column | Default for |
|---|---|---|---|
| `Auto` | from the editor: Small for numbers, dates, toggles; Medium otherwise | — | — |
| `Tiny` | 2 (⅓ column) | `YFormFieldWidthTiny` (96) | `*Id`, `Uf`, house number |
| `Small` | 3 (½ column) | `YFormFieldWidthSmall` (176) | date, number, toggle, CEP, money |
| `Medium` | 6 (1 column) | `YFormFieldWidthMedium` (320) | text, CPF/CNPJ, e-mail, enum choice |
| `Large` | 12 (2 columns; shrinks to 6 to finish a row) | `YFormFieldWidthLarge` (560) | names, titles |
| `Full` | the whole row | none | notes, sections, collections |

The panel lays fields out row by row on a uniform grid (6 tracks per column, one gutter), wrapping like text. **Reworked 2026-11-19 ([06](06-fm-p3-validation-and-layout.md) §2):** a field may start on any track, a row's empty tracks go to its Medium and wider fields (a row of small fields grows each up to a column), a Large field shrinks to one column to finish a row, and width caps apply only when one column is forced on a wide container. The old rule "a field never straddles two columns" left holes and was dropped. This is the old branch's `FormPanel` unit flow with named sizes. Tokens are control-scoped (`Controls/Forms/YForm.axaml`), with `YFormColumnMinWidth` (280) for the column count.

### 4.5 Visual presets (⚑FM14)

A closed set, each one a bundle of existing tokens and input properties, so nobody needs `FontSize`, `Monospace`, `Height`… attributes:

| `FieldPreset` | What it sets | Example |
|---|---|---|
| `Auto` | the type's default | — |
| `Standard` | the input as is | most fields |
| `Emphasis` | larger value text, `Large` control height | the order total, the patient name |
| `Code` | monospace value, no auto-correct | SKU, barcode, internal code |
| `Multiline` | multi-line, grows to 5 lines then scrolls; `Full` by default | notes |
| `Secret` | masked, reveal button | PIN, password |
| `Inline` | `Ghost` appearance, no border until hover | quick edits inside cards and grids |

Form-wide density stays a separate knob: `YForm.Density` → the inputs' existing `Size` (`SizeScale.Small/Medium/Large`, control heights 28/36/40).

### 4.6 Conditions: visible, enabled, read-only (⚑FM11)

All configuration lives **in the model itself** (user decision 2026-11-18: no separate configuration class). Four levels, cheapest first; use the first one that fits:

```csharp
public partial class CustomerEditModel : StateObject
{
    // 1. Modes (static): Create / Edit / View, from the type (Id types) or [Field(EditableIn = …, VisibleIn = …)].
    [Field(EditableIn = FormModes.Create)]
    [Observable] public partial CpfCnpj Document { get; set; }

    // 2. Conventions (dynamic, zero configuration). The generator finds Is{Field}Visible / Can{Field}Edit by name,
    //    reads the expression body to learn which properties it depends on (as Validation infers [Invariant] reads),
    //    and re-evaluates only when one of those changes.
    public bool IsBirthDateVisible => Kind == PersonKind.Person;
    public bool CanEditCreditLimit => !IsBlocked;

    // 3. Named condition, when the property name does not follow the convention or one condition serves several
    //    fields. nameof keeps it compile-checked: a renamed property is a build error, not a silent string.
    [Field(VisibleWhen = nameof(IsCompany), ReadOnlyWhen = nameof(IsBlocked))]
    [Observable] public partial string? StateRegistration { get; set; }
    public bool IsCompany => Kind == PersonKind.Company;

    // 4. Form block, for what attributes cannot say (groups, several fields at once, ordering across groups).
    //    A static method in the model, found by the generator by name and signature, run once when the shape is
    //    first used. Lambdas are typed, so a wrong member is a build error.
    static void ConfigureForm(FormBuilder<CustomerEditModel> form) => form
        .Field(m => m.CompanyName).VisibleWhen(m => m.Kind == PersonKind.Company)
        .Group("Address").StartsCollapsed().Columns(3)
        .Group("Fiscal").VisibleIn(FormModes.Edit);                 // not shown when creating
}
```

Rejected (⚑FM3): a separate `IFormConfiguration<T>` class per model (user, 2026-11-18): the configuration of a field would live far from the field. Also rejected: string expressions in attributes (`[VisibleWhen("Kind == 1")]`), which nothing checks at build time.

Business limits (max installments, allowed options, approval) are **not** conditions: they come from YFex.Rules decisions through `IValidationSource.ConstraintsChanged`, already designed in validation/08. Field-level permissions are a request to Authorization (⚑FM18).

### 4.7 What the generator emits (illustrative)

```csharp
partial class CustomerEditModel
{
    public static FormShape<CustomerEditModel> Form { get; } = new(
    [
        new FieldShape<CustomerEditModel, CustomerId>("Id", static m => m.Id, static (m, v) => m.Id = v)
            { Order = 0, Size = FieldSize.Tiny, Editor = EditorKind.Parsed, VisibleIn = FormModes.Edit, EditableIn = FormModes.None },
        new FieldShape<CustomerEditModel, PersonKind>("Kind", static m => m.Kind, static (m, v) => m.Kind = v)
            { Order = 1, Editor = EditorKind.Segmented, Options = PersonKindOptions.All },
        new FieldShape<CustomerEditModel, CpfCnpj>("Document", static m => m.Document, static (m, v) => m.Document = v)
            { Order = 3, Size = FieldSize.Medium, Editor = EditorKind.Parsed },
        new FieldShape<CustomerEditModel, DateOnly?>("BirthDate", static m => m.BirthDate, static (m, v) => m.BirthDate = v)
            { Order = 6, Editor = EditorKind.Date, IsVisible = static m => m.IsBirthDateVisible, DependsOn = ["Kind"] },
        new ChildShape<CustomerEditModel, AddressModel>("Address", static m => m.Address, AddressModel.Form) { Order = 7 },
        new ListShape<CustomerEditModel, ContactModel>("Contacts", static m => m.Contacts, ContactModel.Form) { Order = 8 },
        // …
    ]);

    [ModuleInitializer]
    internal static void __RegisterForm() => FormShapes.Register(Form);    // lets YForm find the shape from the bound object
}

// Each FieldShape<TModel, T> overrides one method; the generator picks the visitor method that matches T's interfaces,
// so the platform creates YParsedInput<CpfCnpj> with T known at compile time. No MakeGenericType, no Activator.
public override TControl CreateEditor<TControl>(IEditorFactory<TControl> editors) => editors.Parsed(this);
```

```csharp
public interface IEditorFactory<TControl>                                         // proposed, framework-neutral
{
    TControl Text(IFieldShape<string> field);
    TControl Toggle(IFieldShape<bool> field);
    TControl Date(IFieldShape<DateOnly> field);
    TControl Number<T>(IFieldShape<T> field) where T : struct, INumber<T>;
    TControl Parsed<T>(IFieldShape<T> field) where T : struct, ISpanParsable<T>, ISpanFormattable;
    TControl Choice<T>(IFieldShape<T> field) where T : struct, Enum;

}
```

### 4.8 Type hints on value objects (⚑FM5)

> **Decided 2026-11-19 (user): no `[InputHints]`.** Every value type gets its own input (§11, ⚑FM47: `YCpfInput`, `YCnpjInput`, `YCpfCnpjInput`…), so the mask, keyboard and default width belong to that input, not to an attribute on the type. What replaces the hints:
>
> | Need | Comes from |
> |---|---|
> | which editor a `CpfCnpj` field gets | the package that owns the input registers it once, AOT-safe through a generic static: `FormEditors.Register<CpfCnpj>(field => new YCpfCnpjInput())` in a module initializer of `YFex.Entity.Avalonia`; core types are registered the same way by YFex.Avalonia (`Money` → `YMoneyInput`) |
> | default field width | the input: `YForm.SizeProperty.OverrideDefaultValue<YCpfCnpjInput>(FieldSize.Medium)`; `[Field(Size = …)]` on the model still wins |
> | input mask | the input; it may still derive it from the type's positional `[Sensitive]` mask (⚑FM48) |
> | a type with no input yet | `YParsedInput<T>` with the `[Sensitive]` mask if any, `Medium` width; creating the input is the fix (⚑FM47) |
>
> Cost: field width is no longer known to the generated shape at compile time (the form reads it from the editor at render time), and Uno/Blazor each need their own input per type (already true under ⚑FM47). The text below is the rejected proposal, kept for the record.

Domain value objects (`Cpf`, `CpfCnpj`, `Telefone`, `Cep`) live in domain projects; YFex.Avalonia can never reference them. So the type itself says how it is typed in, once, the same way `[Sensitive]` says how it is masked:

```csharp
// YFex.Domain/src/YFex.Entity.Public/CpfCnpj.cs  (attribute proposed in YFex core, no UI reference)
[InputHints(Size = FieldSize.Medium, Keyboard = InputKeyboard.Digits)]          // no Mask: taken from [Sensitive] below
[Sensitive(DataSensitivity.PersonalIdentifier, Mask = "***.###.###-**|##.###.###/####-##", MaskFormat = "F", Identifier = true)]
public readonly partial struct CpfCnpj : ISpanParsable<CpfCnpj>, ISpanFormattable, …
```

- **One mask string, two uses (⚑FM48).** A positional `[Sensitive]` mask already spells the layout of the value: `*` = a hidden character, `#` = a shown one, everything else a literal. Read with every `*` and `#` as a typed slot, `***.###.###-**` *is* the input mask `###.###.###-##` (the `#`-digit syntax `YInputMask` and `YPhoneInput` already use). So a type with a positional `[Sensitive]` mask needs no input mask at all; `[InputHints(Mask = …)]` is only for types that are not sensitive (`Cep`) or whose typed layout differs from the shown one. Placeholder masks (`{email}`, `{last:4}`, `{initials}`) are not positional and give no input mask.
- The two uses stay different: the input mask shapes typing; the privacy mask hides characters from someone who may not see them (details screen, read-only fields, logs).
- The app's Forms generator reads `[InputHints]` from the referenced type's metadata at build time and emits `InputHintsOf<CpfCnpj>.Value = new(…)` in a module initializer, so a hand-placed `YParsedInput<CpfCnpj>` reads the same hints with a generic static, no reflection.
- Core value objects get the same attribute (`Money` → `Small`, `EmailAddress` → `Medium`, `Quantity` → `Small`).

## 5. The view side: three authoring styles, one panel

### 5.1 Fully automatic

```xml
<!-- CustomerEditView.axaml -->
<y:YForm Source="{Binding Customer}" Mode="{Binding Mode}" MaxColumns="3" />
```

`YForm` finds the shape registered for the bound object's type, builds sections (the model's root fields, then one section per group and per child model), creates the editors, binds them, and wires validation through the view model's `IValidationSource`.

### 5.2 Hand-placed fields, editors still chosen for you

```xml
<y:YForm Source="{Binding Customer}" MaxColumns="3">
    <y:YFormSection Header="{y:Text Customer.Contact}">
        <y:YField Field="{Binding Name}" Size="Large" />      <!-- compiled binding: build-checked, path read from it -->
        <y:YField Field="{Binding Document}" />
        <y:YField Field="{Binding Email}" />
        <y:YField Field="{Binding Phone}" />
    </y:YFormSection>

    <y:YFormSection Field="{Binding Address}" Collapsible="True" />   <!-- the child model's own shape, automatic -->

    <y:YFormSection Header="{y:Text Customer.Map}">
        <local:AddressMapView />                                     <!-- any control; still in the column layout -->
    </y:YFormSection>

    <y:YFormRest />                                                  <!-- every field not placed above, in order -->
</y:YForm>
```

- `YField` uses the binding the same way `YTextInput.Field` already does (compiled binding → path), so a typo in a property name is a build error, not a silent empty field.
- `YField` is not a wrapper around a label and an input: it **is replaced** by the editor the shape chooses (or hosts it inside `YHeaderControl` only when that editor has no label of its own, ⚑FM7).

### 5.3 Fully manual, still in the form layout

```xml
<y:YForm MaxColumns="2">
    <y:YTextInput  Description="Nome" Field="{Binding Customer.Name}" y:YForm.Size="Large" />
    <y:YMoneyInput Description="Limite" Field="{Binding Customer.CreditLimit}" />
    <ToggleSwitch  y:YForm.Label="Ativo" IsChecked="{Binding Customer.IsActive}" y:YForm.NewRow="True" />
</y:YForm>
```

Attached properties (`YForm.Size`, `YForm.NewRow`, `YForm.Label`, `YForm.Span`) work on any child, so a screen that needs nothing generated still gets the same columns, sizes and responsive behaviour.

### 5.4 Fluent C# markup (YFex.UI.Markup)

```csharp
Form(vm.Customer, form => form
    .Section("Customer.Contact", s => s
        .Field(c => c.Name).Large()
        .Field(c => c.Document)
        .Field(c => c.Email))
    .Section(c => c.Address)
    .Rest())
    .MaxColumns(3)
    .Mode(vm.Mode);
```

Paths come from `[CallerArgumentExpression]`, as `.Bind(vm.Name)` already does in `BindingExtensions`.

### 5.5 Overrides without leaving "automatic"

```xml
<y:YForm Source="{Binding Customer}">
    <y:FieldOverride For="Document" Size="Large" Preset="Code" />
    <y:FieldSlot For="Address">
        <local:AddressWithMapEditor />           <!-- replaces one field or section with any view -->
    </y:FieldSlot>
</y:YForm>
```

```csharp
// Per type, app-wide (registration stores Func<IFieldShape<T>, Control> in a generic static: AOT-safe)
services.AddYFexForms(forms => forms
    .Editor<CpfCnpj>(field => new DocumentInput())
    .Editor<ProductId>(field => new YLookup<ProductId>(ProductSearch.Provider)));
```

Override levels, narrowest wins: slot in this view → field override in this view → `[Field]` on the model → app editor per type → editor registered by the package that owns the type's input → built-in default.

## 6. The `Form` branch: what to keep (⚑FM15)

`origin/Form` (`0b7bc23`, "Flex e Form paineis", 2026-02) predates the current tree layout (`src/Controls/…`), tokens and the `Y` naming.

| Part | Lines | Keep? | Why |
|---|---|---|---|
| `FlexPanel` / `FlexGrid` / `FlexSizeResolver` unit flow (children take units of a row, wrap, `Fill`, `Auto`, `ForceNewRow`) | ~970 | **keep the algorithm**, rewrite as `YFormPanel` | it is exactly the layout §4.4 needs; gaps become `SpacingScale` tokens, not `FlexGap` |
| `FormSizeResolver` (Compact / Normal / Expanded with hysteresis so the layout does not flicker at a boundary) | 108 | **keep** | becomes "how many columns fit": thresholds from tokens instead of 480/960 px literals |
| `FlexSize` (10 sizes) | 70 | **reduce** to six `FieldSize` values | too many choices; `XSmall`/`XLarge`/`Huge` add little |
| `FormGroup` (header, icon, actions, collapse with animation, implicit vs explicit rows) | 660 | **keep the behaviour**, rebuild on `YExpander`-style template and motion tokens | `FormRow` explicit mode (all rows or no rows, throws on a mix) is a trap; replace with `NewRow` on a field |
| `FormField` attached properties (`Size`, `Units`, `ForceNewRow`, `BindingPath`) | 226 | **keep** `Size`/`NewRow`; drop `Units` (designer-only) and `BindingPath` (compiled binding gives the path) | |
| Designer (`FormDesigner`, `FieldAdorner`, `GroupAdorner`, `DropZone`, permissions `CanHide/CanMove/CanResize/IsLocked`) | ~1,720 | **not in Forms** | end-user screen editing is Composer's job (⚑FM16); a light "personalize" (hide/reorder my fields) could come later on `YDrag` |
| `LayoutDescriptor` / `DescriptorParser` / `DescriptorMerger` | ~860 | **not in Forms** | a runtime layout model is Composer's IR; the merge rules are useful input for Composer |
| `ILayoutPersistence` (`JsonFileLayoutPersistence`, reflection-based JSON) | 247 | **drop** | per-user layout goes to YFex.Persistence / State `[Persist]` (⚑FM17) |
| `FormLayout.TryResolveViaReflection` (scans assemblies, `Activator.CreateInstance` by type name) | — | **drop** | AOT-unsafe, against the ecosystem rule |
| Region and separator comments, Portuguese/English mix | — | drop | comment rules |

## 7. Columns and responsive behaviour

```
 MaxColumns = 3, width 1280                   MaxColumns = 3, width 760 (2 fit)          width 420 (1 fits)
 ┌──────────┬──────────┬──────────┐           ┌──────────────┬──────────────┐             ┌────────────────────┐
 │Id│ Kind  │ Name (Large)        │           │Id│ Kind      │              │             │Id│                 │
 ├──────────┼──────────┼──────────┤           ├──────────────┼──────────────┤             │ Kind               │
 │Document  │ Email    │Phone│Birth│           │ Name (Large → 2 columns)    │             │ Name               │
 ├──────────┴──────────┴──────────┤           │ Document     │ Email        │             │ Document           │
 │ ▾ Address                      │           │ Phone │Birth │              │             │ …                  │
 │  Cep │ Street        │Nº│ City │           │ ▾ Address                   │             │ ▾ Address          │
 └────────────────────────────────┘           └─────────────────────────────┘             └────────────────────┘
```

- `MaxColumns` (1–3, default 2) is the most the form uses; the actual count is how many `ColumnMinWidth` tokens fit, with hysteresis.
- Reading and Tab order is row by row (left to right, then down), the same order as the declaration. Column-major order is rejected: the Tab key would jump down a column while the eye reads across.
- A section can set its own `Columns` (`[FieldGroup("Address", Columns = 3)]`), never more than the form has.
- `Full` fields, child sections and collections always take a whole row.

## 8. Child models and collections (⚑FM12, ⚑FM13; collections detailed later)

| Property type | Default rendering | Options |
|---|---|---|
| child model (`AddressModel`) | a section: header from the label, a hairline start border, its fields inside, collapsible; **collapsed sections are not built until opened** | `Inline` (no header, fields merged into the parent's flow), `Card`, `Dialog` (a summary line + "Edit" opens it) |
| list of simple children (≤ 6 fields, all fit one line) | `YDataGrid` with editable cells, a new-item row, delete per row, reorder by `YDrag` | `Cards` |
| list of complex children | a list of collapsible cards, each a sub-form; "Add" appends and opens one; reorder by drag or Alt+arrows | `MasterDetail` (grid + form of the selected row), `Dialog` (grid + edit in a dialog) |

Paths follow Validation's: `Contacts[2].Phone`, so a server violation on that path lands on that cell.

## 9. More ideas that remove boilerplate

Each idea: what it is, the problem it removes, an example. All APIs here are *proposed*.

### 9.1 Three models, each with its own shape (⚑FM27 ✅, ⚑FM41 ✅)

**Decided (user, 2026-11-18).** A record is shown through **three models, each with its own boundary**, not one model reused everywhere. The details screen holds much more than the form (purchase history, appointments, convênio), and the list holds much less.

| Model | Used by | Holds | Comes from |
|---|---|---|---|
| `CustomerRow` | the list (`YDataGrid`, filter bar) | the few columns the list shows | the list query |
| `CustomerEditModel` | the form (`YForm`) | what the user may type; `[ValidatesAs<…Command>]` | the get query, mapped (⚑FM45) |
| `CustomerDetailsModel` | the details screen | read-only data plus related lists: purchases, appointments, convênio | its own details query |

Each model gets its own generated shape, and each control reads the shape of the model it is bound to. That still removes boilerplate (grid columns come from `CustomerRow`, no hand-typed column list), but no model leaks into another screen.

```csharp
[Form] public partial class CustomerRow : StateObject                      // list
{
    [Observable] public partial PartyName Name { get; set; }
    [Observable] public partial CpfCnpj Document { get; set; }
    [Observable] public partial Money Balance { get; set; }
}

[Form, ValidatesAs<Customer.Commands.UpdateCommand>]
public partial class CustomerEditModel : StateObject { … }                 // form

[Form(Kind = FormKind.Details)]
public partial class CustomerDetailsModel : StateObject                    // details screen
{
    [FieldGroup("Contact")]      [Observable] public partial PartyName Name { get; set; }
    [FieldGroup("Contact")]      [Observable] public partial CpfCnpj Document { get; set; }   // masked unless the user may see it
    [FieldGroup("Convenio")]     [Observable] public partial ConvenioRef? Convenio { get; set; }
    [FieldGroup("Purchases")]    public StateList<PurchaseRow> Purchases { get; } = [];      // its own row model, loaded on first open
    [FieldGroup("Appointments")] public StateList<AppointmentRow> Appointments { get; } = [];
}
```

```xml
<y:YDataGrid ItemsSource="{Binding Customers}" AutoColumns="True" />     <!-- columns from CustomerRow -->
<y:YForm     Source="{Binding Editor.Model}" />                          <!-- fields from CustomerEditModel -->
<y:YDetails  Source="{Binding Details}" Layout="Tabs" />                 <!-- text, not inputs; each group a tab built on first open -->
```

`YDetails` renders a shape as read-only text (privacy masks applied) and lists as grids from their own row models; it is the read-only counterpart of `YForm`, and part 2 (02 §2) places it in the CRUD page. Adding `Email` to the list means changing `CustomerRow`; to the form, `CustomerEditModel`. Each change is deliberate, which is the point of separate boundaries.

### 9.2 Create and Edit in the edit model; no View mode (⚑FM10 ✅, ⚑FM53)

**Decided (user, 2026-11-18).** There is no "View mode" of the edit model: viewing is the details model (9.1). What remains is the small difference between creating and editing a record:

```csharp
public partial class CustomerEditModel : StateObject
{
    [Field(EditableIn = FormModes.Create)]
    [Observable] public partial CpfCnpj Document { get; set; }           // typed when creating; shown as text when editing
    [Observable] public partial PartyName Name { get; set; }             // editable in both
}
```

```xml
<y:YForm Source="{Binding Editor.Model}" Mode="{Binding Editor.Mode}" />  <!-- Create or Edit -->
```

**⚑FM53 (pending).** One edit model for both (recommended: Create and Edit usually differ in one or two fields), or a separate `CustomerCreateModel` when the create screen asks for different fields (for example a first purchase or an initial credit limit approval). The design supports both; the question is the default.

### 9.3 Eject (⚑FM28), in plain steps

**The situation.** With automatic forms there is **no `.axaml` file** for the customer form: `<y:YForm Source="{Binding Customer}"/>` builds the fields while the app runs, from the model. That is the whole point: no XAML to maintain.

**The problem.** Once in a while one screen needs a layout the automatic form cannot produce: a map beside the address fields, a photo next to the name, two fields joined in one custom control. Overrides (§5.5: `FieldOverride`, `FieldSlot`) cover most of these. When they don't, you must write that screen's XAML by hand, and you start from an empty file: 30 `YField` lines, sections and sizes, typed from memory.

**Eject = "give me the XAML of this automatic form" so I can start from it.** It is a "Save as" for a generated form:

1. In a debug build, right-click the form → **Copiar como XAML** (or run `yfexForms eject CustomerEditModel`).
2. You get the markup that matches what you were seeing:

   ```xml
   <y:YForm Source="{Binding Customer}" MaxColumns="3">
       <y:YFormSection Header="{y:Text Customer.Contact}">
           <y:YField Field="{Binding Name}" Size="Large" />
           <y:YField Field="{Binding Document}" />
           <y:YField Field="{Binding Phone}" />
       </y:YFormSection>
       <y:YFormSection Field="{Binding Address}" />
   </y:YForm>
   ```

3. Paste it into `CustomerEditView.axaml` and change what you need (add `<local:AddressMapView/>` beside the address section).

**What you keep and what you lose.** Each `YField` still picks its editor, mask, validation and permissions from the model. What becomes manual is only the **placement**: a property added to the model later does not appear in this file by itself; the generator warns "`Email` is not placed in CustomerEditView.axaml".

**Is it needed?** It is a convenience, not a building block. If overrides and the manual style (§5) are enough, ⚑FM28 can be dropped with no effect on the rest of the design.

### 9.4 Form profiles (⚑FM34)

**What.** A named subset of fields of the same model, chosen per screen.

**Problem it removes.** At the POS the cashier registers a customer in five seconds (name, CPF, phone); the back office fills thirty fields. Without profiles you write two models, two sets of rules and two mappings to the same command.

**Example.**

```csharp
[Field(Profiles = "quick")] [Observable] public partial PartyName Name { get; set; }
[Field(Profiles = "quick")] [Observable] public partial CpfCnpj Document { get; set; }
[Field(Profiles = "quick")] [Observable] public partial Telefone? Phone { get; set; }
[Observable] public partial AddressModel Address { get; set; }          // full profile only
```

```xml
<!-- POS dialog --> <y:YForm Source="{Binding Customer}" Profile="quick" MaxColumns="1" />
<!-- back office --> <y:YForm Source="{Binding Customer}" />
```

Validation already has strictness profiles (`ProfileId`), so the same word can make only the quick fields required in the POS and everything required in the back office.

### 9.5 Keyboard-first data entry (⚑FM35 ✅)

**What.** Forms that a fast typist can fill without the mouse.

**Problem it removes.** ERP and pharmacy users type all day; Tab-only navigation, mouse-only Save and errors found by scrolling slow them down.

**Example.**

```xml
<y:YForm Source="{Binding Customer}" EnterMovesNext="True" />
```

The cashier types `João Silva` ↵ `12345678909` ↵ `11987654321` ↵ Ctrl+S. If the CPF check digit is wrong, Save does not go through: focus jumps to the CPF field, its message shows under it, and the summary at the bottom lists it. Esc in a field puts back the value it had before you started typing in it.

### 9.6 Drafts (⚑FM17 ✅ drafts: yes)

**What.** A half-filled form is saved locally while you type and offered back when the form opens again.

**Problem it removes.** A crash, a closed tab or a navigation away loses ten minutes of typing.

**Example.**

```xml
<y:YForm Source="{Binding Customer}" DraftKey="customer-new" />
```

Reopening "Novo cliente" shows a bar: *"Rascunho de hoje 14:32 encontrado. Restaurar · Descartar"*. Drafts are kept by YFex.Persistence (⚑FM17). Fields whose type is `[Sensitive]` are stored sealed through YFex.Cryptography or left out of the draft; that choice is part of ⚑FM17.

### 9.7 Change summary (⚑FM26 ✅ optional)

**What.** Before saving an existing record, show what changed, let the user undo one change, and send the same list to the audit log. **Optional** (user, 2026-11-18): off by default, turned on per form with `<y:YForm ShowChangeSummary="True"/>`; the audit diff is written either way.

**Problem it removes.** "Who changed the credit limit?" and "I didn't mean to change that" both need a list of changes that today nobody builds.

**Example.** `[Trackable]` (YFex.State) already remembers the original values, so the form can show:

```
 3 alterações em João Silva
   Telefone        (11) 3456-7890  →  (11) 98765-4321     [desfazer]
   Limite          R$ 500,00       →  R$ 1.000,00         [desfazer]
   Observações     —               →  "cliente antigo"    [desfazer]
                                         [Cancelar]  [Salvar]
```

The same three lines go to YFex.Audit with the actor (YFex.Actors), masked where the type is `[Sensitive]`.

### 9.8 Paste or AI fill (⚑FM23 ✅)

**What.** Fill a form from free text instead of typing field by field.

**Problem it removes.** Customer data often arrives as a WhatsApp message or an e-mail; today the user copies each piece by hand.

**Example.** The user pastes into the form:

```
Nome: João Silva — CPF 123.456.789-09 — cel (11) 98765-4321 — joao@exemplo.com.br
```

- **Without AI:** types that can find themselves in text (`IExtractable<T>`; `Telefone.TryExtract` exists) fill CPF, phone and e-mail directly.
- **With AI**, a separate **"Colar com IA" (AI paste)** option in the form's menu, never automatic (user, 2026-11-18): the shape exports a JSON schema (Validation's `JsonSchemaWriter` already does this from `TypeShape`); an AI step returns `{ "Name": "João Silva", … }`, which is parsed through the same value types, so a wrong CPF is still rejected.

Filled fields show a small mark until the user touches or confirms them; nothing is saved without a person pressing Save.

### 9.9 References to other records (⚑FM20 ✅)

**Decided (user, 2026-11-18).** Models carry what they need, never a bare id. A field that points to another record has a small summary type the query fills, so the form and the details screen show it with no extra request:

```csharp
public readonly record struct SupplierRef(SupplierId Id, PartyName Name, CpfCnpj Document);

[Observable] public partial SupplierRef Supplier { get; set; }     // shows "Distribuidora São Paulo Ltda · 12.345.678/0001-90"
```

Only **changing** it needs more: the field's "change" button opens a search ("dist sp" → matches as you type) and the choice replaces the whole `SupplierRef`. That picker comes from the Search + Capabilities plan ([02-record-lookup](../search-capabilities/02-record-lookup.md)); Forms only places it. A `*Ref` type with no picker registered is shown read-only.

### 9.10 Stable automation ids (⚑FM25 ✅)

**What.** Every generated editor gets the field path as its automation id.

**Problem it removes.** UI tests, screen readers and YFex.Automation need a stable name for each input; hand-written ids are forgotten or drift.

**Example.** The CPF input gets `AutomationProperties.AutomationId="Customer.Document"`. A UI test or an automation step writes:

```csharp
await form.Field("Customer.Document").TypeAsync("12345678909");
await form.Command("Save").InvokeAsync();
```

and keeps working when the layout changes, because the path comes from the model, not from the screen.

### 9.11 Device input (⚑FM24)

**What.** Fields can be filled by a device handled by YFex.Devices.

**Problem it removes.** At the pharmacy counter the scale weight and the barcode are typed by hand, with typos.

**Example.**

```csharp
[Observable] public partial Mass Weight { get; set; }              // Mass: the input shows a "ler balança" button
[Field(Preset = FieldPreset.Code, Device = DeviceInput.Barcode)]
[Observable] public partial string Barcode { get; set; }           // a scan fills it while it has focus
```

The input asks YFex.Devices for one reading; the device code is never in the form or the model.

### 9.12 Generated tests

**What.** Tests produced from the shapes, so every form is checked without someone writing tests per screen.

**Problem it removes.** A refactor silently changes a form (a field disappears, a size changes) and nobody notices until a user complains.

**Example.**

```csharp
[Fact]
public void Customer_form_shape_is_unchanged() =>
    FormShapeSnapshot.Assert(CustomerEditModel.Form, "snapshots/CustomerEditModel.form.txt");
    // the text file lists fields, order, sizes, groups, modes; a change shows as a diff in review
```

Plus GalleryShots renders every `[Form]` light and dark at three widths, and StressKit types hostile values (very long text, emoji, a pasted page) into every generated editor.

## 10. Pitfalls and how the design avoids them

"Settled" = the design already removes it; there is nothing left to do but follow the design. "Checked in" = the design has an answer, and that phase must prove it with a test, a measurement or an AOT publish before it is called done.

| # | Pitfall | Avoided by | When |
|---|---|---|---|
| 1 | **Attribute soup**: ten attributes per property, nobody can read the model | type hints + conventions first; one `[Field]` with named arguments; conditions in code (§4.1, §4.6) | settled; checked in FM-P2 on the Farma models |
| 2 | UI attributes leak into public contracts and domain modules | annotations only on UI models; value types carry a core attribute with no UI reference (⚑FM4, ⚑FM5) | settled; an analyzer warning in FM-P2 for `[Field]` on a non-UI-model type |
| 3 | Reflection sneaks back in. **XAML compiled bindings are fine**: `x:DataType` / `x:CompileBindings` bindings are turned into code at build time, so `YField Field="{Binding Name}"` written in XAML uses no reflection. The risk is only for fields the form **creates at run time**, where there is no XAML for the compiler to see. There, `new Binding("Name")` is a reflection binding (not trim-safe), and so are `TypeDescriptor`, `Activator` and `MakeGenericType` | generated accessors (`static m => m.Name`) and the typed visitor, so the form never looks anything up by name. Avalonia 12 also has `CompiledBinding.Create<TIn, TOut>(x => x.Name)` for bindings built in code (an expression tree the compiler builds, no string path); whether it publishes with no AOT warnings is measured in the spike | checked in FM-P0 (Native AOT publish of the spike, zero IL warnings) and in every later phase's AOT smoke |
| 4 | Generators cannot see each other's output (State emits the partial property bodies, Validation emits `TypeShape`) | the Forms generator reads only the **declarations** (partial properties, attributes, types), which are in source; at run time it calls other libraries through their contracts (`IValidationSource`) | checked in FM-P0 |
| 5 | Two labels: `YTextInput` has a floating description, a wrapper adds another | the form sets the input's own `Description`; `YHeaderControl` only for editors without one (⚑FM7) | checked in FM-P1 (gallery shots) |
| 6 | Three error sources shown in three places: parse errors (draft), shape violations, rule decisions | one presenter per level (§12): the input's helper line shows the draft error first, then visible violations by severity; summaries per section and form | checked in FM-P3 |
| 7 | Over-automation: the last 20 % of screens cannot be expressed and people bypass the system | five override levels (§5.5); the manual style keeps validation wiring; eject (§9.3) | checked in FM-P4 (rebuild one real Farma screen in each style) |
| 8 | Big forms freeze navigation (R9 found ~250 ms builds) | collapsed sections and tabs built on first open; the details screen (`YDetails`) uses text, not inputs | measured in FM-P0 (60-field form), budget enforced from FM-P1 |
| 9 | Layout flickers when the width sits at a breakpoint | hysteresis from the old `FormSizeResolver` | checked in FM-P1 (resize test) |
| 10 | Required inference surprises (`string` vs `string?`) | follow Validation (P5: inference off by default); the asterisk shows only what `FieldConstraints.Required` says | settled; checked in FM-P3 |
| 11 | Records and init-only contracts cannot be two-way bound | edit models are `StateObject`s; `[ValidatesAs<TCommand>]` maps them to the command (`ToT()`); contract → model mapping is ⚑FM45 | part 2 |
| 12 | Field paths drift between UI, Validation and server violations | one path syntax (core `Paths`), taken from the compiled binding or the shape, never typed by hand | checked in FM-P3 (server violation lands on the right field, including `Contacts[2].Phone`) |
| 13 | Labels become English property names in a pt-BR app | catalog keys by convention (`Customer.Name`) through core localization; the humanized name is only the development fallback, and a missing key is a warning in debug (⚑FM21) | checked in FM-P2 |
| 14 | A second form designer appears next to Composer | the old designer is not ported; Forms emits a shape Composer can render (⚑FM16, ⚑FM29) | settled once ⚑FM16 is answered |
| 15 | Generic controls in XAML (`YParsedInput<CpfCnpj>` needs `x:TypeArguments`) | generated forms create them in code; hand-written XAML uses `YField` and lets the shape pick | checked in FM-P4 |
| 16 | One API on every platform | metadata and enums framework-neutral in `src/Core`; Avalonia first, Uno/Blazor later with `yfex-ui-port` | checked whenever a platform port starts |
| 17 | Duplicate value types (`Email` in YFex.Domain vs core `EmailAddress`, `Telefone` vs core `PhoneNumber`) | settled in the domain's own plan before hints are written twice: [`YFex.Domain/docs/value-types-plan.md`](../../../../YFex.Domain/docs/value-types-plan.md) ⚑VT1–VT2, atlas F48 (⚑FM31) | before FM-P2 |
| 18 | A value type has no input, so the form falls back to a plain text box and loses mask, paste cleanup and live checks | rule §11: every value type gets a real input, designed from the type's own behaviour; a missing one is a build warning from the generator | settled as a rule; each new input is built when a model first uses its type |
| 19 | Drafts or change summaries write personal data to disk or logs in clear | `[Sensitive]` fields are sealed or left out of drafts; summaries and audit use the type's mask (§9.6, §9.7) | checked in FM-P5 |

## 11. Rule: every value type gets its own input (⚑FM47)

**If a value type has no input, the input is created** — never a plain `YTextInput` bound to a string. The input is designed from what the type knows and does, not from a generic template. Placement follows the dependency rule:

| Value type lives in | Its input lives in | Why |
|---|---|---|
| YFex core (`Money`, `Quantity`, `EmailAddress`, `PhoneNumber`, `Percentual`, `ValidityPeriod`…) | `YFex.Avalonia/Controls/Inputs` (and later Uno, Blazor) | infrastructure for infrastructure types; most exist already |
| a domain project (`Cpf`, `Cnpj`, `CpfCnpj`, `Rg`, `InscricaoEstadual`, `Cep`…) | a separate package next to the types, named `{DomainPackage}.Avalonia`: **`YFex.Domain/src/YFex.Entity.Avalonia`**, **`YFex.Fiscal/src/YFex.NFe.Avalonia`**…, built with the YFex.UI rules (`Y` prefix, tokens, states, stress test) (user, 2026-11-19) | YFex.UI is infrastructure and never depends on a domain package; each domain UI package references YFex.Avalonia and its own `.Public` types, so an app takes only the domains it uses |

Alternative recorded in ⚑FM47: move Brazilian document types into core (rejected by the project-kind rule: a country's rules are domain).

**Two layers so a new input is small:**

1. `YParsedInput<T>` / `YValueInput<T>` (exist) + the `[Sensitive]` mask give **any** parsable type, for free: the positional mask, digit-only typing, caret kept across literals, paste cleanup (strip everything that is not a slot character, then re-apply the mask), commit through `T.TryParse`, the invalid-draft state (`InvalidDraftText` exists), required/limits from `IValidationSource`.
2. The type's own input adds only what is specific to it.

**Checklist for a new value-type input** (what "creative, following the type's functions" means in practice):

| Area | Ask of the type | Example: `CpfCnpj` | Example: `Rg` |
|---|---|---|---|
| Typing | which characters, which layout | digits only; mask switches from CPF `###.###.###-##` to CNPJ `##.###.###/####-##` when the 12th digit is typed (the union's two cases); from 2026 the alphanumeric CNPJ: letters allowed in the first 12 positions | digits plus a final `X`; layout varies by issuing state (UF selector as prefix, like `YPhoneInput`'s region) |
| Paste | what people paste | `123.456.789-09`, `12345678909`, `12.345.678/0001-95` with spaces or line breaks, a CNPJ inside a sentence (`TryExtract` when the type is `IExtractable`) | `12.345.678-X`, `MG-12.345.678` |
| Copy | what the user wants on the clipboard | formatted by default; Ctrl+Shift+C copies digits only (systems that reject punctuation); nothing when the value is masked for this user | formatted |
| Live check | what can be known before commit | check digits verified as soon as the last digit is typed: `:invalid` with "dígito verificador inválido", without waiting for blur | length per UF |
| Display | how it reads when not editing | `F` format; in `View` mode or without permission the `[Sensitive]` mask (`***.456.789-**`) and a reveal button (⚑FM19) | same |
| Keyboard | soft keyboard on touch | numeric | numeric with a key for `X` |
| Extras | anything the type enables | a suffix badge "CPF" / "CNPJ" showing which case was detected; "consultar CNPJ" action slot (app command, not in the control) | — |
| Quality floor | YFex.UI rule 5 | all states, focus ring, accessible name ("CPF ou CNPJ"), StressKit run with hostile pastes, gallery page | same |

Per-type behaviour that is **not** UI (check-digit maths, extraction, formatting) stays on the type. The input calls it; it never re-implements it.

## 12. Showing validation failures (⚑FM50)

Every failure already has a clear sentence available, because of two existing pieces:

- **Message catalog** (validation/10, decision D6): a violation is a code + field path + values (`Length`, `min 2`, `max 80`), never a pre-built string; the catalog turns it into text at the edge, per culture and with tenant overrides, and State's `ErrorItem.Message` formats it once. Field names come from the same catalog (`CreateCustomer.Document` → "CPF/CNPJ").
- **Rules `Explanation`** (validation/06 §5, `Decision.Explain(catalog, culture)` exists): for a business-rule outcome it says *why*: which rule limited the value, which did not apply and why not ("12x sem juros — requer pagamento com cartão de crédito"). That comes from the Rules generator's condition splitting, so it is precise, not generic.

Where each failure shows:

| Level | Where | Content |
|---|---|---|
| Field | the helper line under the input (the inputs already have it) | the first visible message by severity; draft parse errors first. Colour and icon by severity (error, warning, info) |
| Section | a summary strip **at the bottom of each section** (and of each child model / collection card), visible once something in it was touched or a save was tried | "2 problemas em Endereço": each line is the field name + message; clicking one focuses the field (opens the section if collapsed) |
| Form | a summary **at the bottom of the form**, next to the Save button (and a count badge on the command bar for long forms) | form-level violations (empty path, cross-field invariants), server violations without a field, plus a link per section with problems |
| Rule decision | under the field it limits, an "ⓘ por quê?" link that opens `YRuleBreakdown` with the `Explanation` in a flyout | "Parcelas: até 6x (tabela Parcelamento v42)"; needs-approval shows the approval action (validation/08 §8) |
| Tab / collapsed section | the tab header or section header | an error dot with the count, so problems in hidden places are not missed |

Timing follows `IValidationSource` (touch on blur, everything on save): no red fields before the user typed anything. On save with errors, focus goes to the first invalid field in reading order and the form summary is announced to screen readers.

## 13. Field permissions: with or without an Authorization change (⚑FM18)

Today's Authorization already gives the client what a form needs: typed permissions (`[PermissionCatalog]`), `IAuthorizationContext.HasPermission(in Permission)`, a signed permission snapshot for offline, and command policies that the server checks again. What it lacks is a policy keyed by **member path** ("who may see / edit `Customer.CreditLimit`").

### Without changing Authorization (recommended now)

```csharp
public partial class CustomerEditModel : StateObject
{
    // the convention from §4.6, fed by a permission: the form needs nothing else
    public bool CanEditCreditLimit => Caller.HasPermission(SalesPermissions.EditCreditLimit);
    public bool IsCostPriceVisible => Caller.HasPermission(PricingPermissions.SeeCost);
}
// Caller = the IAuthorizationContext the page view model hands to the edit model (or the same properties live on the
// view model when the form binds there); the model never resolves services itself.
```

For many fields with the same pattern, a tiny helper value (proposed, in `YFex.UI.Forms`) keeps it to one line each and gives the three states a field can have:

```csharp
public readonly record struct FieldAccess(bool Visible, bool Editable)          // Hidden, ReadOnly, Editable
{
    public static FieldAccess From(IAuthorizationContext caller, Permission? see, Permission? edit) => …;
}

// the ConfigureForm block in the model (§4.6)
static void ConfigureForm(FormBuilder<CustomerEditModel> form) => form
    .Field(m => m.CreditLimit).Access(c => FieldAccess.From(c, see: null, edit: SalesPermissions.EditCreditLimit))
    .Field(m => m.CostPrice).Access(c => FieldAccess.From(c, see: PricingPermissions.SeeCost, edit: PricingPermissions.EditCost));
```

### With a field-level policy in Authorization

```csharp
// Authorization (proposed): one table, editable by an operator, keyed by contract member path
policies.Member<Customer>(c => c.CreditLimit).See(Any).Edit(SalesPermissions.EditCreditLimit);
// the form asks IFieldAuthorization.Access("Customer.CreditLimit", caller) and needs no model code
```

### Comparison

| | Without (model + helper) | With (Authorization member policies) |
|---|---|---|
| Code per field | one property or one fluent line | none in the model |
| Who can change it | a developer | an operator at run time (if the table is editable) |
| Server enforcement of **edit** | the command policy already rejects the command; if only one field is restricted, the handler (or a Rules `Deny`) checks "changed without permission" | the same table drives a generic server check of changed members |
| Server enforcement of **see** | the query returns the value masked or empty for that caller (handler + Privacy mask); hiding it in the form alone is not security | the same table drives query masking |
| Offline | the permission snapshot already covers `HasPermission` | the snapshot must carry member policies too |
| Cost | none now | a new Authorization feature (table, snapshot field, server hooks) |

**Recommendation:** build without; record "with" as pending, to revisit when (a) the same member rule is repeated across many screens, or (b) operators must change field access without a release. Either way, a field the user may not see must be removed by the **query**, never only by the form.
