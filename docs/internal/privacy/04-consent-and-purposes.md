# 04 — Purposes, legal bases & consent

## 1. Why a consent ladder is not enough (⚑P8)

LGPD requires every processing operation to have **a purpose** (art. 6 I) and **one legal basis** (art. 7; art. 11 for sensitive
data). Consent is only one of ten bases. When consent is the basis, it must refer to **determined purposes** ("generic
authorizations are void", art. 8 §4). It must be **highlighted** for sensitive data (art. 11 I) and **revocable at any time** by an
easy procedure (art. 8 §5).

Today's `ConsentLevel { None, Functional, Analytics, Full }` is a ladder. It already broke down once: `ConsentRecord` had to add six
booleans (browser data, window titles, network capture, process detail, file activity, traffic interception), because "Full"
covered too much. Business apps need more again: a pharmacy customer may accept the loyalty program, refuse marketing e-mails, and
accept that their medication history is kept for pharmaceutical care. Meanwhile the NF-e with *CPF na nota* is a legal obligation
that must **not** be presented as consent (asking implies the customer can refuse or withdraw, and they cannot).

**Before** (today)

```csharp
if (_consent.IsAllowed(ConsentLevel.Full)) CollectBrowserData(fields, errors);      // all-or-nothing above Analytics
```

**After**

```csharp
if (consent.Allows(TelemetryPurposes.Values.BrowserData)) CollectBrowserData(fields, errors);   // one purpose, one decision
```

The ladder survives as a **preset** in the Profiling UI: one button, "Analytics", grants a bundle of purposes (§8).

## 2. `LegalBasis` (closed set: the law defines it)

```csharp
namespace YFex.Privacy;

/// One legal basis per purpose. Values map to LGPD art. 7 (personal data) and art. 11 II (sensitive data).
public enum LegalBasis : byte
{
    Consent = 1,               // art. 7 I   · art. 11 I (specific and highlighted, for specific purposes)
    LegalObligation = 2,       // art. 7 II  · art. 11 II a   — NF-e/NFC-e, SNGPC, accounting, labour records
    PublicPolicy = 3,          // art. 7 III · art. 11 II b   — public administration only
    Research = 4,              // art. 7 IV  · art. 11 II c   — research bodies, anonymized when possible
    ContractPerformance = 5,   // art. 7 V                    — NOT available for sensitive data
    LegalProceedings = 6,      // art. 7 VI  · art. 11 II d   — regular exercise of rights in judicial/administrative/arbitral processes
    LifeProtection = 7,        // art. 7 VII · art. 11 II e
    HealthProtection = 8,      // art. 7 VIII· art. 11 II f   — health professionals, health services, sanitary authority
    LegitimateInterest = 9,    // art. 7 IX                   — NOT available for sensitive data; subject may object (art. 18 §2)
    CreditProtection = 10,     // art. 7 X                    — NOT available for sensitive data
    FraudPrevention = 11,      // art. 11 II g only           — sensitive data in identification/authentication processes
}
```

Generator check YFP0022: a purpose whose categories include a special category (health, biometric, …) must use one of
`Consent, LegalObligation, PublicPolicy, Research, LegalProceedings, LifeProtection, HealthProtection, FraudPrevention`.
`FraudPrevention` is rejected for non-sensitive purposes (it exists only in art. 11).

## 4. Privacy notices (versioned text, per tenant)

Consent is only valid for the text the person actually saw. A notice is stored with a SHA-256 of its exact content, and every
consent entry points to `(notice id, version, hash)`.

```csharp
namespace YFex.Privacy.Consent;

public sealed record PrivacyNotice(
    string NoticeId,                         // "loyalty-terms"
    int Version,                             // monotonically increasing per tenant + notice
    string Locale,                           // "pt-BR"
    string Title,
    string Text,                             // Markdown; what is shown, byte for byte
    ImmutableArray<string> Purposes,         // purpose keys covered
    DateTimeOffset EffectiveFrom,
    bool MaterialChange,                     // true → existing grants for these purposes become NoticeChanged (re-ask)
    ControllerIdentity Controller,           // tenant legal name, CNPJ, address (art. 9, art. 41)
    DataProtectionOfficer Officer,           // encarregado: name + contact channel (art. 41 §1)
    ReadOnlyMemory<byte> ContentHash);       // SHA-256 over Title + "\n" + Text (UTF-8)

public interface IPrivacyNoticeStore
{
    ValueTask<PrivacyNotice?> GetCurrentAsync(string noticeId, string locale, CancellationToken cancellationToken);
    ValueTask<PrivacyNotice?> GetAsync(string noticeId, int version, string locale, CancellationToken cancellationToken);
    ValueTask PublishAsync(PrivacyNotice notice, CancellationToken cancellationToken);   // audited; versions are immutable
}
```

Notices are **per tenant**: in a multi-tenant SaaS each tenant (the pharmacy) is the **controller** (*controlador*) and the YFex
operator is a **processor** (*operador*, art. 5 VI–VII, art. 39). The tenant's identity and DPO appear in its notices. Defaults
ship with the app and are copied per tenant on first use.

## 5. The consent ledger (⚑P9)

### 5.1 Entries are immutable; state is a fold

```csharp
namespace YFex.Privacy.Consent;

public enum ConsentDecision : byte { Granted = 1, Denied = 2, Withdrawn = 3 }

public enum ConsentChannel : byte { Application = 1, Web = 2, PointOfSale = 3, Paper = 4, Api = 5, Import = 6 }

public enum DataSubjectKind : byte { Person = 1, ApplicationUser = 2, Device = 3 }

/// Who the decision is about. Person = a customer/patient/employee known to the tenant (DataSubjectId);
/// ApplicationUser = the logged-in user of the app; Device = an installation (telemetry before login).
public readonly record struct DataSubjectReference(DataSubjectKind Kind, string SubjectKind, string Value);   // Value: id text

public sealed record ConsentEntry(
    Guid EntryId,                            // client-generated (offline), idempotent on the server
    string Tenant,                           // top scope key (controller)
    DataSubjectReference Subject,
    string Purpose,                          // purpose key (persisted form)
    ConsentDecision Decision,
    string NoticeId, int NoticeVersion, ReadOnlyMemory<byte> NoticeHash,
    ConsentChannel Channel,
    string? CollectedBy,                     // operator principal when an employee recorded it (POS, phone, paper)
    DataSubjectReference? Guardian,          // parent/guardian for children (art. 14 §1)
    DateTimeOffset RecordedAt,               // device clock
    DateTimeOffset? ReceivedAt,              // server clock, set on ingest
    string DeviceId,
    ReadOnlyMemory<byte> Evidence,           // optional: SHA-256 of a signed form scan, PIN-pad confirmation code, OTP challenge id
    ReadOnlyMemory<byte> DeviceSignature,    // ECDsa P-256 over the canonical entry (offline entries, §7)
    DateTimeOffset? ExpiresAt);              // optional validity (e.g. marketing: re-ask after 24 months)

public interface IConsentLedger
{
    ValueTask AppendAsync(ConsentEntry entry, CancellationToken cancellationToken);   // idempotent by EntryId; never updates or deletes
    IAsyncEnumerable<ConsentEntry> ReadAsync(DataSubjectReference subject, CancellationToken cancellationToken);
    ValueTask<ConsentSnapshot> GetSnapshotAsync(DataSubjectReference subject, CancellationToken cancellationToken);
}
```

Only a data subject erasure removes ledger entries, and it keeps a tombstone (07 §6).

### 5.2 Folding rules (normative)

For each `(subject, purpose)`:

1. Order entries by **corrected time** = `RecordedAt + device clock offset` (offset measured at sync, logging 05 §5), then by `ReceivedAt`.
2. The **latest** entry wins, except that a `Withdrawn`/`Denied` entry within the skew window (default ±5 min) of a `Granted`
   entry wins regardless of order. When in doubt, the subject's "no" prevails.
3. A `Granted` whose `ExpiresAt` passed → `Expired`.
4. A `Granted` whose notice has a newer version with `MaterialChange = true` → `NoticeChanged` (the app re-asks; processing under
   that purpose stops until then).
5. Purposes whose basis is not `Consent` → `NotRequired` (the ledger is not consulted).

### 5.3 The snapshot: what hot paths read

```csharp
namespace YFex.Privacy.Consent;

public enum ConsentStatus : byte { NotRequired, NotAsked, Granted, Denied, Withdrawn, Expired, NoticeChanged }

/// Immutable fold of a subject's ledger. Allows() is a bit test: no allocation, no lock.
public sealed class ConsentSnapshot
{
    public DataSubjectReference Subject { get; }
    public long Version { get; }                             // ledger position folded; changes on every new entry
    public DateTimeOffset AsOf { get; }

    public bool Allows(Purpose purpose);                     // NotRequired or Granted
    public ConsentStatus StatusOf(Purpose purpose);
    public PurposeSet Granted { get; }                       // for session attributes and the logging join (§9)
}

/// Bit set over Purpose.Id: inline 128 bits, overflow array beyond (apps with > 128 purposes are unusual).
public readonly struct PurposeSet : IEquatable<PurposeSet>
{
    public bool Contains(Purpose purpose);
    public PurposeSet With(Purpose purpose);
    public PurposeSet Without(Purpose purpose);
    public static PurposeSet Empty { get; }
}
```

## 6. Withdrawal (art. 8 §5, art. 18 IX)

Withdrawal must be as easy as granting, and it must take effect everywhere. Each purpose declares what happens to data already
collected under it (configuration, §11):

| `WithdrawalEffect` | Meaning | Example |
|---|---|---|
| `StopProcessing` (default) | no new processing for the purpose; existing data follows its retention rule | loyalty points history kept for accounting |
| `DiscardPending` | also drop buffered, not-yet-shipped data collected under the purpose | telemetry batch and offline queue (today: shipped, see 01 §1) |
| `EraseData` | also start an erasure for the purpose's categories (07) | marketing contact list |

Propagation:

1. The server appends the entry, folds a new snapshot and **invalidates** the Fusion compute method
   `IConsentQueries.GetSnapshot(subject)` (same mechanism as `CallContextSignals.PermissionsChanged`, validation D29).
2. Connected devices receive the invalidation and refetch. Offline devices apply their **local** entries immediately (a withdrawal
   made on the device itself takes effect at once) and catch up on reconnect.
3. The `privacy.consent.staleness` metric reports how old the snapshots on devices are. An alert fires above the tenant's limit.
4. The withdrawal is audited (Logging Audit channel), and `ConsentChanged` events reach in-process subscribers (Profiling, the
   loyalty module).

## 7. Proof and offline devices

- **Proof** = the ledger entry + the notice version/hash + the device signature + the audit record (hash-chained, logging 07 §2).
  Today's `TelemetryEventQueueSerializer` rebuilds consent as `(UtcNow, "restored")`. After the migration each queued event carries
  the `EntryId` of the consent that covered it, so the proof survives restarts.
- **Offline entries** are signed by the **device key** (ECDsa P-256), the infrastructure already used for offline rule approvals
  (validation D34, `OverrideTokens`). The server verifies the signature against the device's registered public key. An unknown or
  revoked device puts the entry in quarantine: it is not lost, but it does not count until an operator reviews it.
- **Operator-collected consent** (POS: "o cliente aceita participar do programa?") is weak evidence if only the operator clicks.
  The design offers stronger channels without making them mandatory: confirmation on the PIN pad (`YFex.Devices`), an OTP/link sent
  to the customer's phone or e-mail, or a signed paper form (scan hash in `Evidence`). The tenant policy chooses the minimum channel
  per purpose. Sensitive purposes default to "customer confirms, not operator" (§11).

## 9. Logging integration (session joins)

Logging records **operations** (legitimate interest / legal obligation, no consent). Profiling records **behaviour** (consent). They
share `session.id` (logging 05). The logging session attributes carry `privacy.consent.version` and the granted telemetry purposes
(as keys). The log server joins a session's behaviour events with its operation traces **only if** `telemetry.behaviour` was granted
for that session. Every consent entry is also written to the **Audit** channel (`Privacy.Consent.Granted/Withdrawn`), which gives the
hash-chained proof.

## 10. Authorization and Cqrs

Authorization answers "**may the caller** do this?". Consent answers "**did the data subject** agree to this purpose?". They are
different principals: the cashier sends the command, the customer is the subject.

**✍ Dev writes** (aggregate configuration; parsed syntactically by the Cqrs generator like `.Validation(...)`, D27)

```csharp
public sealed class FidelidadeConfiguration : IAggregateConfiguration<Fidelidade>
{
    public void Configure(AggregateBuilder<Fidelidade> b)
    {
        b.Privacy(p => p.DefaultPurpose(FarmaPurposes.Values.LoyaltyProgram));     // purpose of every message of the aggregate

        b.Command<AcumularPontosCommand, Saldo>()
         .RequirePermission(Permissions.FidelidadeOperar)
         .Privacy(p => p.RequireConsent());              // subject = the message's SubjectKey/Identifier member (generated)
    }
}
```

**⚙ Generated**: the Cqrs generator finds the subject member through the personal-data shape (`Cliente: CustomerId` with
`SubjectKey`). Two candidates are ambiguous, and YFP0024 asks for `p.Subject(c => c.Cliente)`. It emits a `PrivacyDescriptor` per
message (purposes, subject member accessor, consent requirement).

**📦 Framework**: `PrivacyStage` in the server pipeline, after authorization and before rules:

```csharp
// (sketch)
if (descriptor.RequiresConsent)
{
    var subject = descriptor.ReadSubject(in message);                         // generated accessor, no reflection
    var snapshot = await consentQueries.GetSnapshot(subject, ct);              // Fusion compute: cached, invalidated on change
    if (!snapshot.Allows(descriptor.Purpose))
        return Error.ConsentRequired(descriptor.Purpose.Key, snapshot.StatusOf(descriptor.Purpose));   // typed, serializable (wire v2)
}
```

**👁 Result** on the client: `ApplyServer` maps `ConsentRequired` to a non-field error. The Avalonia consent prompt (phase 7) offers
"Pedir consentimento do cliente" with the notice for that purpose.

Purposes also flow into the **inventory and ROPA** (03 §5): a command without any purpose (no default, no explicit) is listed as
`purpose: unspecified`, which is a review item, not a build error.

## 12. Children and adolescents (art. 14, Enunciado CD/ANPD 1/2023)

- Art. 14 caput: data of children **and** adolescents is processed in their **best interest**.
- Art. 14 §1: when the basis is **consent** and the subject is a **child** (under 12, ECA), consent must be specific and highlighted,
  given by at least one parent or legal guardian.
- **Enunciado CD/ANPD 1/2023** (binding on the ANPD): data of children and adolescents may be processed under **any** basis of art. 7 or
  art. 11, provided the best interest prevails in the concrete case. A pediatric prescription dispensed under a legal obligation needs
  no parental consent. A loyalty account for a 10-year-old (consent basis) does.

The library provides the rule (`ConsentRules.RequiresGuardian(birthDate, asOf)`: true for consent-based purposes when the subject is
under 12) and the `Guardian` field on ledger entries. For adolescents (12–17), the tenant policy decides whether a guardian is also
required for each consent purpose (conservative default: yes for health purposes). Games, contests and apps must not condition
participation on more data than necessary (art. 14 §4). That is a review item, not code.
